# Maintenance and coverage protocol

One capability row means a defined requirement, not a completed feature. Add owners, priority and implementation evidence as work begins. Every active capability needs its exact data/model/operational specification and independent acceptance record. Domain-level source lists are a reading map; formulas and code must cite the exact specification used.

Use stages: specified; source-verified; implemented; independently validated; replay/paper proven where applicable; enabled for a declared profile; deprecated. Record analysis, simulation and live maturity separately when those differ. Never upgrade every row because one test suite passed.

New instruments require a lifecycle/accounting profile. New models require a model card. New datasets require a data contract. Strategies require a hypothesis/experiment record and all trial history. Live enablement requires an operational profile and account-specific permission evidence.

Review changes in broker APIs, exchange specifications, datasets, accounting/tax rules and dependencies before the affected capability is used. Trigger review after unexplained P&L, model drift, provider revisions, incidents or a failed reconciliation. Keep previous versions and reasons for changes.

Expand the knowledge base where a concrete workflow needs depth. Record unreviewed methods as candidates rather than copying formulas from unsourced web summaries. Preserve negative research and known limitations. Link requirements to evidence, not marketing claims.
